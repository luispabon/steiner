# Claude subscription internals

User guide: [Claude subscription](../user/claude-subscription.md).

The `claude_subscription` provider drives the signed-in `claude` CLI as a stateful adapter. The CLI is not a stable protocol contract, so this page describes the implementation the tests cover.

## Process pool and session identity

`ClaudeSubscriptionPool` owns CLI processes. Parent normal calls are pooled by `TransportSession`, falling back to the parent transport session and then `default`. Model and effort are not part of the key. Calls for one key are serialized, and a process is reused until teardown. A process that exits is evicted, and its successor reseeds.

Only parent normal calls persist (`claudeSubPersists`). Advisor calls key the pool by their advisor transport session plus `|advisor` (`claudeSubAdvisorSessionKey`): `<session>-advisor|advisor` for the parent and `<session>-subagent-advisor|advisor` for sub-agents. Advisor, sub-agent, and summary calls store no backend state. A parent turn returns an opaque backend state holding the CLI session ID, transport session, sync record counts and digests, final message UUID, and a prompt/tools fingerprint. It holds no message text.

A model or effort change reuses the live process: `set_model` for the model and `apply_flag_settings` for `effortLevel`.

The pool runs `claude --version` and `claude auth status`. The status must report `authMethod` `claude.ai` and `apiProvider` `firstParty`. `loggedIn` is decoded as an explicit boolean pointer. Any explicit `loggedIn:false` is classified as signed out when auth status exits successfully or with exit code 1, and bounded stdout is retained long enough to make that classification. Missing or malformed booleans, timeouts, and unrelated errors remain unknown. The provider never reads a credential file.

The locator is a tracked single-flight job. A signed-out result marks the completed job eligible for one synchronized replacement on a later explicit acquire. No waiter mutates or closes an active job. The advisor usage-recovery path uses a pool-owned, tracked single-flight fresh auth check with an 8 second operation timeout (`claudeSubFreshAuthTimeout`). Callers may stop waiting, but the check remains bounded, and pool shutdown cancels and joins it. When it confirms external logout, the leased session is retired and the request returns an actionable error; no request is replayed. Advisor sessions idle for 60 minutes are reaped (`claudeSubDefaultIdleTTL`). Other sessions stay open until the pool closes them. Session close is bounded by 10 seconds (`claudeSubSessionCloseTimeout`), and pool shutdown by 15 seconds.

`STEINER_CLAUDESUB_RECORD` names a directory for raw stdout capture. The directory is created with mode `0700`, and each per-session JSONL file is written with mode `0600` under an encoded name, so session keys cannot escape the directory. Recordings contain prompts, tool data, file contents, and account details. Before committing a fixture to `internal/provider/testdata/claudesub/`, keep only the representative lines and redact emails, organization IDs, paths, and file contents.

## CLI invocation

Normal sessions use this process shape:

```text
claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --model <model> --tools "" --strict-mcp-config --setting-sources= --disable-slash-commands --settings {"autoCompactEnabled":false,"fastMode":false} --permission-mode dontAsk
```

Additional flags:

- `--system-prompt-file` carries the private system prompt.
- With tools, a private MCP config and an allowlist for `mcp__steiner__*` are added.
- Calls that do not persist add `--no-session-persistence`.
- Restoring stored state adds `--resume <session-id>` and, when a target UUID is set, `--resume-session-at <uuid>`. Forks add `--fork-session`.
- Summary helpers set `--max-turns 1`.
- Effort `none` maps to `--thinking disabled`. A recognized effort (`low`, `medium`, `high`, `xhigh`, `max`) enables adaptive thinking and passes `--effort`. Empty or unknown effort is adaptive without `--effort` (`claudeSubEffort`).

The child environment strips `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`, and `CLAUDE_CODE_ENTRYPOINT`. These values override inherited ones: `CLAUDE_CODE_DISABLE_FAST_MODE=1`, `CLAUDE_CODE_RETRY_WATCHDOG=0`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1`, `CLAUDE_CODE_SILENT_TURN_REMINDER=0`, `CLAUDE_CODE_TOTAL_TOKENS_REMINDER=off`, `CLAUDE_CODE_TODO_REMINDER_MODE=off`, and `CLAUDE_CODE_DISABLE_GIT_INSTRUCTIONS=1`. `MAX_MCP_OUTPUT_TOKENS` is set to a bounded value. Forcing `CLAUDE_CODE_RETRY_WATCHDOG=0` turns off the CLI's unattended retry mode: the CLI does not wait out a capacity error or a usage-limit reset window, and follows its normal bounded retry count before reporting the limit. Steiner then ends the turn on the resulting `*UsageLimitError`.

The CLI still injects account and environment context that these switches do not remove. See [Privacy](../user/claude-subscription.md#privacy).

## Loopback MCP host

Each tool-enabled session starts an MCP host on `127.0.0.1` with an OS-chosen port and a bearer token. Requests without the token are rejected. Tools are published as `mcp__steiner__<name>`, and names over the 64-character limit (`claudeSubToolNameMax`) are shortened with a hash suffix.

The stream registers each tool use ID. The `tools/call` whose `_meta["claudecode/toolUseId"]` matches receives the result. While the tool runs, the handler sends progress notifications every 20 seconds (`claudeSubHeartbeat`).

## Control messages and stream decoding

Conversation uses four control requests: `set_model` when the requested model differs from the live model, `apply_flag_settings` to change effort, `get_usage` before a new user message for the usage gate, and `interrupt` when pending tool work is stale or a call is cancelled. `initialize` is used only by model discovery.

The decoder waits for the assistant-message boundary before treating a tool call as complete, which prevents duplicate text. A tool input that does not parse is recorded on that call as `argument_decode_error`, and the turn continues. The CLI's `__unparsedToolInput` sentinel (`UnparsedToolInputKey`) carries the raw text of an input the CLI could not parse. The decoder checks it against the streamed input.

Every `system` envelope is ignored except `api_retry`, which the CLI emits when it retries a retryable API failure itself. `(*claudeSubDecoder).decodeSystem` accepts it only in `claudeSubPhaseStreaming`, so a notice after message_stop or the terminal result is dropped. The item carries the attempt, the permitted retry count, the delay clamped to a non-negative `time.Duration`, the HTTP status when there was a response, and the failure category; a malformed notice is dropped with a debug record instead of failing the turn. `claudeSubConsume` emits it as a warning `ChatChunk` with `RetryAttempt`, `RetryMaxAttempts` and `RetryDelay` set, `RetryReset` false, and the unexported `cliRetry` notice set, because the CLI retries before it produces output and discards nothing. `claudeSubAPIRetryNotice` reads that notice: the chunk does not close the pre-output retry window, does not trigger a pending replacement warning, and does not report the warning in the advisor's reported-emit wrapper. `claudeSubNormalTurn` also records that the CLI retried in this attempt and then declines the Steiner pre-output retry, since a fresh process would only repeat the wait the CLI already completed. The agent maps a streamed chunk with `RetryAttempt` set and no reset to `output.DiagnosticKindRetry`, and the advisor emits that kind for both this chunk and the `RetryReset` chunks that carry a diagnostic, so the live `retrying N/M` indicator covers streaming calls. A non-streaming call folds its chunks (`foldClaudeSubChunks`), where every notice of that call collapses into one summary warning (`claudeSubAPIRetrySummary`) naming the count and the last failure with its status; any other diagnostic stays one warning each. `claudeSubEventIsOverage` resolves the `api_retry` subtype before its notification probe and returns false for it, so a malformed notice cannot fail the pool closed; usage-limit detection reads only `rate_limit_event`.

## Transcript synchronization

The sync record is append-only. User and tool messages are compared by content digest (`claudeSubDigest`). Images are excluded from the digest because steiner strips image data after use, and image fingerprints are compared separately. The placeholder text that replaces an image is frozen into the message before its first delivery (`freezeImagePlaceholders` in `internal/agent`), so cleanup removes only the bytes and the digest never changes afterwards. Only bytes present on a request message are an image delivery claim: a stripped history message claims nothing, and replacing or adding images to an already recorded message still fails. The checkpoint stores the per-entry delivered fingerprints (`claudeSubBackendState.SyncEntryImages`, digests only), which is the authority `claudeSubResumeEntries` uses once the bytes are gone. A reseed stores only the fingerprints of the images its flattened transcript actually carries, so the rebuilt record, later live appends and checkpoint restore agree; a checkpoint from before per-entry fingerprints existed reseeds once and then stabilises, and a checkpoint whose stored fingerprints disagree with the history it describes reseeds instead of being trusted. Assistant entries are matched by tool-call IDs, since the CLI may normalize their text. Any other rewrite, omission, or reorder makes the live process unusable for that request: the process is retired, and the request forks or reseeds.

## Session recovery

A new parent process restores stored state only when the stored CLI session ID, prompt/tools fingerprint, and final message UUID match the request history (`claudeSubRestoreFor`). Every restore forks: `claudeSubRestoreFor` always returns Fork, so the resume runs `--resume <session> --resume-session-at <uuid> --fork-session`. A fork never appends to the transcript file an old, orphaned or just-retired process may still hold open, and the earlier turns it hides stay untouched; the probe measured the resumed fork warm (cache read 1155, created 48). The next Done checkpoint carries the fork's own session ID, because the record takes the ID the CLI reports, so the chain stays correct from then on. Any failed check reseeds. A live process that accepts the history is reused as is, even if the prompt or tool set has changed. When a live process rejects the request, the stored state is restorable, and no live process for this key is being replaced by a retry, the process is retired and the request resumes the stored state on a new one (`claudeSubAttachSession`). A prompt and tools fingerprint mismatch, a missing final uuid, a history that does not carry the stored prefix, a tool message in the request suffix, or a request the stored record cannot append still reseeds.

A reseed sends the whole non-system history as one user transcript message. Images still in memory are included, and stripped image data does not return. Tool calls in the history are rendered as text.

An assistant message that carries `IncompleteText` is the partial steiner recorded locally when a turn ended early. A partial always has text, because `commitInterruptedAssistant` rejects a blank response, so a non-empty `IncompleteText` is the whole marker. `claudeSubTranscript` renders it under `claudeSubPartialLabel`, which says the text is an interrupted assistant partial, untrusted and locally observed, and ended before the response was complete. The exact streamed text follows inside a fence the text cannot contain: `claudeSubPartialFence` derives the tag from the partial's SHA-256 and returns a fence absent from the text: it rehashes at most `claudeSubPartialFenceRounds` times and then appends an incremented counter until the fence is absent, which terminates because the text is finite. The fence is therefore deterministic, and a `>>>`, a `[user]` or a forged tag inside the text stays text. The interrupted note that the agent appends to the provider projection's `Content` is not rendered, because `IncompleteText` holds the raw text. A complete assistant message renders under the `[assistant]` label with its content and tool calls. `IncompleteText` is `json:"-"` local provenance: no provider sends it, `claudeSubDigest` hashes role, content, and name only, and no persisted state carries it.

A stdin line refused by the CLI's limit fails the turn with `send flattened reseed transcript` wrapped around the limit error (`claudeSubLineTooLargeError`), so an oversized reseed is identifiable. `errors.As` still reaches the typed limit error.

An interrupted run commits its streamed text locally as an incomplete assistant message. That message is not part of the sync record steiner keeps for the CLI transcript, so it cannot be appended as an input message. `claudeSubInterruptedTail` recognises the request suffix such a stop leaves: a user message, at most one assistant partial (`claudeSubDrainedPartial` shape) that is not the last message, and the new user messages. `claudeSubRestoreFor` runs the dry plan without that partial, so the stopped-turn shape restores, and the resume sends the partial as a quoted note instead (see "Stopped parent turns"). No request error is raised.

A generation whose backend state was cleared has nothing to restore, so its next request starts fresh and reseeds from the preserved conversation. Backend state is saved with the session, so a crash between retiring a process and saving the session can leave the previously persisted state on disk. That saved checkpoint may be older than the retired transcript, and resuming from it after such a crash is unverified.

## Cancellation safety

A cancelled turn cannot prove event ownership by itself. When a delivery reached the CLI and the caller cancelled it before the turn's terminal chunk, the CLI keeps producing that turn's events, and they cannot be attributed to a later call. `claudeSubRecoverInterrupted` therefore tries to make the process provably clean before giving up on it.

A cancelled delivery is drainable when `claudeSubInterruptedDrainable` holds: the turn's terminal result was not read, the delivery recorded no assistant entry, the record holds nothing but the user and tool entries this delivery appended (`claudeSubDeliveryTail` against the ledger length `claudeSubDeliver` recorded after adopting the planned record), and the session is neither unsafe nor gone and saw no overage. A delivery that only resolved tool results is therefore drainable, which is what a stop in an agent tool loop needs: the CLI continues the same turn after the results, and the stop lands while the model streams its next message. `claudeSubDrainInterrupted` then sends `interrupt` on a context derived from `context.WithoutCancel`, so the cancelled caller cannot abort the wait, and reads the session queue to the terminal result. The whole drain, acknowledgement included, shares one deadline (`claudeSubDrainTimeout`, 5 seconds). It emits nothing to the caller, records nothing in the ledger, decodes only result envelopes, and applies overage and usage-limit detection to every event it reads. A session that ends or closes revokes the wait through `s.gone`, so a draining call never holds pool shutdown or teardown.

The drain accepts only the CLI's own aborted result (`claudeSubDrainAborted`): an error result whose `terminal_reason` is `aborted_streaming` or `aborted_tools`, or, for a CLI version that publishes no terminal reason, the `error_during_execution` subtype. A success result means the turn finished before the interrupt landed, and any other result, a malformed envelope, an error control response, a closed connection, a timeout, or an overage or usage limit is a failed proof. After an aborted result the CLI emits nothing until the next user input (probe timelines E1 to E6, CLI 2.1.316), so the drain also checks the queue once without waiting (`claudeSubQueue.tryPop`) and treats any event already there as a failed proof. That check is best effort: it sees only events already routed into the session queue, so it catches an event that arrived before the check and cannot see one the CLI sends later. The absence of later events rests on the live probe of CLI 2.1.316, not on a proof.

On a proven drain the process serves the next call. Every open MCP call without a stored result is retired through the host (`claudeSubMCPHost.cancelUnresolved`), the session's stream-time registrations are cleared (`claudeSubDiscardPending`), the ledger is marked drained (`claudeSubSync.markDrained`), and no replacement notice is recorded. The drained state is separate from `interrupted`: it accepts one relaxed text-only assistant message at the suffix head (`claudeSubDrainedPartial`), records it and never sends it, and a second assistant, tool calls, images or reasoning remain `errClaudeSubHistoryChanged`. The relaxed shape differs from the D22 partial in two ways: the turn number the agent stamped is accepted, and `IncompleteText` must be set, so the marker alone separates the kept partial from any other text-only assistant. `commitSent` clears the state, so it covers exactly one delivery, and `planSummary` refuses it. The CLI transcript holds the CLI's own partial text and its `[Request interrupted by user]` marker, which the model sees on the following turn; the agent's kept partial stays local history. `markDrained` sets the state only when the record's trailing entries are exactly the user entries (`commitSent`) and tool-result entries (`commitToolResult`) that delivery wrote, so a record another writer touched leaves it undrained and the next request reseeds.

## Stopped parent turns

A parent stop is recovered without discarding the CLI session, in one of two ways.

A drained stop keeps the live process, and the stored checkpoint the next parent request carries is exactly one stopped delivery behind the live record. `claudeSubSync.drainedMatches` accepts that shape: the drained flag is set and the record is not tainted, the drained delivery's start index (`drainedBase`) equals `stored.SyncEntries`, the record grew past it, every entry after it is a user or tool entry the stopped delivery wrote, and `checkpointAt` over the stored entry count equals the stored state field for field. `claudeSubLiveAccepts` then plans the request against the live record, which still enforces the stopped turn's entries by digest and accepts the one relaxed partial, and the suffix must carry a user message after that partial. The delivery appends to the same process, sends no warning, and its Done checkpoint covers everything, including the partial entry steiner recorded but never sent. Records that do not match exactly (another `drainedBase`, a tainted record, a cleared drained state, an assistant in the tail) are refused, and the stopped user line edited in the request is caught by the plan, both of which fall through to the resume path.

When the live process cannot be used, a restorable stored state resumes instead: the process exited, a failed drain abandoned it, the live record rejected the request (checkpoint or plan) for this owner, or no process is pooled after a restart. `claudeSubAttachSession` retires the live process, confirms its teardown, and spawns the successor with `--resume <stored session>`, `--resume-session-at <stored final uuid>` and `--fork-session`, which hides the stopped turn in the CLI transcript and leaves the original file alone. Every resume forks, including the one after a restart, so no old or orphaned process can write the same file. Exit confirmation is `pool.retireConfirmed`: the session close path must return, which means the process wait returned and the router is done. Any exit status counts, including a failure status or a signal, because the close path returns only the tree-termination result. A teardown that misses its deadline or fails does not confirm, and the request reseeds with a new session (`claudeSubReseedUnconfirmed`). A stale-pending drain retry keeps forcing a reseed: it may not resume a dangling tool call.

A resume with a kept partial sends one user line whose blocks are the stopped user content, the note from `claudeSubStoppedReplyNote`, and the new user content, because the CLI accepts only user input. The note states that the reply ended before it finished (a user stop, a usage limit and an error all leave the same partial, so it claims no cause), quotes the text verbatim between `claudeSubPartialFence` markers, marks it untrusted and possibly incomplete, and says the new message may supersede it. It caps the quote at 64 KiB, keeping the first 48 KiB and the last 16 KiB on UTF-8 boundaries with `[... N bytes elided ...]` between them. `claudeSubResumeDelta` builds that delivery and sets the record to the stored prefix plus one entry per suffix message, so the record equals the request history and its digest chain stays reproducible. Without a partial the request travels as the plain delta: the stopped user messages and the new ones in one line.

The call reports how it recovered: `drained_reuse` for the live reuse, `resume_after_stop` when the retired process was abandoned by a stop or the request carried a kept partial, and `resume_after_mismatch` when a live record no longer matched the request without any stop. A drained reuse reports no warning and a resume after a restart reports nothing; a live reject records a replacement notice because that process was discarded unexpectedly, so the recovering call reports the replacement warning and no flattened replay, since nothing is flattened. Every reseed fallback keeps the flattened or combined warning. A tool message in the request suffix reseeds: a resumed process registers no pending call, and `claudeSubDeliver` refuses a result with no pending call.

Every other cancelled delivery abandons the process. `claudeSubSession.abandon` marks the process unsafe and records a replacement notice for its key in the pool. Two other mid-turn stops abandon the process the same way, because the CLI may keep going after each: a stale-pending interrupt in `claudeSubFinishPending` whose drain is not proven, and a `rate_limit_event` that ends the turn inside `claudeSubConsume`.

A stale pending call whose delivery already read the turn's terminal result is retired through the host without an interrupt: the CLI is idle, so an interrupt would only produce a stray result. The handles are resolved as interrupted and the stream-time registrations cleared, no drain or interrupted state is claimed, and the request then follows the ordinary mismatch and restore rules. When the delivery has not read its result, `claudeSubFinishPending` uses the same drain. After the interrupt it reads the CLI's own aborted result, which the probe shows arriving after an assistant tool_use echo, a user tool_result echo and the `[Request interrupted by user for tool use]` marker. Consuming that result is what stops a later call from reading it as its own. On a proven drain the stale handles are resolved with an interrupted result, every other open host call without a stored result is retired, `s.pending` is cleared, and the record is marked interrupted exactly as before. A failed drain abandons the process; `claudeSubAttachSession` then retires it and re-attaches the same request to a fresh process, which reports the replacement, while the advisor and in-place summary paths return the error and let the existing unsafe-session retirement handle the next request.

Every path that could reuse an unsafe process retires it first: `claudeSubAttachSession` for parent and sub-agent calls, `claudeSubAdvisorTurn` for advisor calls, and the summary entry points `claudeSubTryParentFork`, `claudeSubParentInPlace`, and `claudeSubSubAgentSummary`. As a backstop, `claudeSubDeliver` refuses an unsafe process with `errClaudeSubSessionUnsafe` and retires it, so a caller that misses the check still cannot write to it or read its queue.

The replacement notice lives on the pool, not on the session, so eviction, idle reaping, or a failed replacement startup cannot lose it. It is in-memory state: it vanishes with the pool, so a steiner restart before the next request for that key reports no warning. `claudeSubReplacementReport` emits the notice before the recovering attempt's first streamed chunk and does not clear it; the call clears it only through `confirm` after it succeeded. The warning therefore claims only what is certain, that a process behind an earlier unfinished turn was discarded, and never claims a resume, a transcript rebuild or a fresh process, because a retried attempt or a reused live process would make such a claim wrong. An attempt that produces no output reports nothing and leaves the notice pending.

Summaries make no replacement claim. A summary is an auxiliary request: replacing the unsafe parent it found, or reseeding its ephemeral helper, recovers nothing of the conversation, so the notice stays pending for the request that continues it. Helper keys (`key + claudeSubSummarySuffix`) never record a notice.

A conversation reseed also reports that prior context was replayed as one flattened user message (`claudeSubFlattenedReseedWarning`). `claudeSubNormalTurn` sets `claudeSubReplacementReport.flattened` from `claudeSubAttachResult.reseed`, so every reseed branch qualifies: no stored state, a failed restore or checkpoint match, a rejected live process, an exited process, and the retry after a failed resumed attempt. The attempt decides its single warning when it emits it: a pending notice alone reports the replacement wording, a reseed alone the flattened wording, and both at once report `claudeSubReplacedAndFlattenedWarning`, one message carrying both facts. The flattened notice is per request: it is not stored on the pool, so the call that delivered the flattened transcript reports it once and a later call cannot repeat it. A failed call that already reported it does not have it repeated by the next request unless that request reseeds again, which reports its own flattened replay. Summary reseeds and advisor snapshot renders report neither, because a summary is auxiliary and an advisor always renders its snapshot as one message, whether or not anything was reseeded.

The warning travels as a `ChatChunk` diagnostic (`Diagnostic` plus `Severity` `warning`). The agent's streaming turn and the advisor's streaming turn emit it as a provider diagnostic event. A non-streaming call folds it into `ChatResponse.Warnings`, which the agent's non-streaming paths and the advisor's non-streaming path emit as the same event. A folded call that fails returns no response, so its buffered warning never reaches the user; because the notice is cleared only on success, it stays pending and the next request reports it. A streaming call that delivered the warning and then failed also keeps the notice pending, so the next request may repeat the warning: a duplicate, never a silent loss.

A cancellation that lands on a terminal chunk does not mark the process: a final assistant message or a tool-call message ends the delivery and its events are consumed, and a later call settles a stale pending tool call through `claudeSubFinishPending`. A cancellation the usage gate absorbs, before anything is written to the CLI, also leaves the process reusable.

The unsafe process is retired when a later call uses its key, not at cancellation time. Until then its abandoned turn keeps running, and its events stay in the session queue that retirement discards. Pool shutdown retires it too.

## Failure recovery

A parent delivery that fails without a user stop is classified by `claudeSubRetryDecision` (`claudesub_retry_decision.go`) from the attempt's facts: output already streamed, the CLI retried its own request, a tool call in flight, a restorable stored checkpoint, the recovery budget spent, and the caller's context.

Only a failure before any output is retried (`claudeSubRetryPreOutput`), and only when the request carries a stored checkpoint the retry can fork-resume. It needs typed evidence that the CLI connection ended: `errClaudeSubConnClosed`, which the event queue and a failed write both return, or the `error_during_execution` result with no terminal reason that a crashed CLI synthesises. The process is retired with `retireConfirmed`, the call waits out `claudeSubRetryBackoff` (1s, then 3s, ending as soon as the caller stops), and attaches again with `forceReseed` false, so the retry resumes the stored checkpoint in a fork. The retry attach runs in fork-only mode (`claudeSubAttachSession`) and has one acceptable outcome: a fork resume of the stored checkpoint. A spawn spec without a fork target is refused before any process starts, a primed process another call pooled is never delivered on, and a reseed requirement another same-key call recorded before the attempt or while it waited on the process lease fails the attach. Every refusal ends the call with its original failure and keeps the marker for the next user request. The recovery metric, log line and notice are recorded only after that attach forked the checkpoint, so a refused retry reports nothing. Resuming the CLI session means the prompt cache can stay warm, but a fork at a checkpoint does not guarantee a cache hit. A retry never reseeds. When the teardown cannot confirm the exit the call ends with its original failure and keeps the reseed marker, so the next user request reseeds with `unconfirmed` instead of resuming a process that may still be alive, and a fresh transcript keeps no cache. One call spends at most `claudeSubRetryMaxRecoveries` attempts, and each retry it actually performs is logged with its attempt, subtype, terminal reason and action.

A failure after output is never recovered: text or thinking already emitted to the caller ends the call with its failure, so the caller keeps what it streamed. That covers a crash, a closed connection, and a mid-response API error. Automatic continuation is rejected because live probe runs measured unreliable joins: when the cut fell after a whole line the continued reply lost the line break between the last two items. Thinking alone also counts as output and is never retried, and the caller's kept partial is the streamed text only: reasoning is not preserved. The next request recovers warm instead, through the stopped-turn machinery. The agent keeps the streamed text as an incomplete assistant message (`IncompleteText`), `claudeSubInterruptedTail` recognises that suffix, and the request retires the live process (reporting the replacement) or starts with none, then resumes the stored checkpoint in a fork with the stopped-reply note quoting the partial (`claudeSubResumeDelta`). A live process is reused instead only when `claudeSubLiveAccepts` proves its record matches, which a failed delivery never does: its record holds the delivered user line and no assistant entry for the streamed text.

Nothing else is recovered: a user stop or cancelled context, a usage limit, gate or overage refusal, paid extra usage, an unrecognised rate-limit status, a mid-response `api_error` before any output (the CLI already exhausted its own retries), an attempt the CLI retried itself, an aborted result (`aborted_streaming`, `aborted_tools`, or the `[Request interrupted by user` marker a CLI without terminal reasons writes), a result with no terminal reason whose text carries the CLI's own API failure wording (`claudeSubAPIFailureMarkers`: `api error`, `server error mid-response`), any other error subtype such as `error_max_turns`, auth, billing, credit, permission or invalid-request text from the CLI's result text (`claudeSubPermanentFailureText`; the stderr tail and control-response text are excluded, so an incidental stderr word never blocks a retry), a decode or result-envelope error, an oversized stdin line, an oversized stdout line (`bufio.ErrTooLong`, which fails closed because the line never reached Steiner), an unsafe session, an attempt with a tool call in flight (`claudeSubRetryRefused` and the `Pending` fact, which reads the session's stream-time registrations and `claudeSubMCPHost.hasOpenCalls`), a sub-agent request or any other request without a stored checkpoint, every advisor, in-place summary and summary-helper call, and any other error that is not typed closed-connection evidence, such as a control-request timeout or a gate transport failure from a process that may still be alive.

A delivery that has already handed the CLI its tool results and then cannot write its user line abandons the process: the CLI may be running a turn Steiner never reads, so the session is marked unsafe, a replacement notice is recorded, the call returns `errClaudeSubUnconsumedTurn`, and nothing is replayed on that process. A request that would add nothing to the record its process already holds is refused before delivery with `errClaudeSubEmptyDelivery`, both when a live process accepts it (`claudeSubLiveAccepts`) and by a guard in `claudeSubDeliver`. Writing nothing would leave the delivery waiting on an idle CLI for a turn that never started, and a cancellation there could only drain an idle process.

Once a retry's attach forked the stored checkpoint, the call emits one warning chunk carrying the recovery notice, `RetryAttempt`, `RetryMaxAttempts` and `RetryDelay`, with `RetryReset` false, which the agent and the advisor surface as `output.DiagnosticKindRetry` on the activity row. A retry that never attached emits no notice. That notice is separate from the replacement warning (`claudeSubReplacedProcessWarning`) and the flattened-replay warning (`claudeSubFlattenedReseedWarning`, or their combined form): the notice says a retry is happening, the other two say what happened to the process or the transcript behind an earlier turn. One call reports at most one of the replacement or flattened warnings: an attempt after one that already reported it reports nothing, and a call that reported the notice clears it on success. The terminal chunk reports `retry_pre_output` as the call's recovery when a retry ran.

## Compaction

`statefulUsageReachesSelectedThreshold` in `stateful_compaction_guard.go` compares the last response's `PromptTokens` with `ModelTokenBudget.CompactionThresholdTokens` when it is set. Otherwise `statefulUsageAboveThreshold` compares against `CompactionThreshold`, a fraction that `deriveEffectiveLimits` sets to 0.70. `compactionUsageThreshold` (also 0.70) is the fallback when that is zero. For this provider, `PromptTokens` is the CLI's total input from the terminal assistant message (`claudeSubUsage.toUsageStats` sums input, cache creation, and cache read tokens). The CLI's result usage covers the whole query, including tool round-trips, so it is not used. A request that does not fit also triggers compaction, as it does for every provider.

A stored compaction summary projects to a user-role conversation message with the fixed historical-context wrapper. `CompactionSourceMessages` counts that message when the generation already has a summary, so a follow-up summary's source prefix includes it and the sync record matches the request.

Summary routing is owned by `claudeSubSummaryTurn` (`claudesub_turn_summary.go`), tried in this order:

- Sub-agent (`ParentTransportSession` set): the summary is marked in place on the sub-agent's own process, which is then retired.
- Parent, tried first (`claudeSubTryParentFork`): when the stored state matches the live checkpoint and fingerprint, an ephemeral helper forks the stored CLI session at the source tail UUID (`--fork-session`, `--max-turns 1`) under `key + claudeSubSummarySuffix`. The live parent is untouched.
- Parent, when forking is not possible or fails before output with an error other than a usage limit (`claudeSubParentInPlace`): the summary is appended in place to the live transcript, and the process is retired.
- Parent with no live process, or whose record cannot take the summary: the request is reseeded on an ephemeral helper with no persistence.

If a compaction candidate omits the leading summary (a summary-prefix-stripped view) while the live CLI transcript holds the projected summary as its first user message, the source prefix does not match. Both parent summary paths decline rather than rewrite the transcript: `claudeSubForkSourceOf` cannot produce a source tail uuid, and `planSummary` returns `errClaudeSubSummaryNoPlace`. The request cold-reseeds on an ephemeral helper (`claudeSubReseedSummary`), whose `claudeSubReseedDelta` sends the whole non-system request history as one user transcript and which is retired afterwards. No live-process history is rewritten.

When a live parent exists, an in-place parent summary retires it whatever the summary's outcome. `claudeSubDeliverTainted` taints the record before the first write, and `claudeSubParentInPlace` retires and releases the process afterwards, so it is never reused. The terminal chunk of a successful in-place summary carries `ClearBackendState` (`claudeSubClearOnDone`). A failed or cancelled in-place summary may or may not deliver a terminal chunk, so `claudeSubParentInPlace` also marks its error with `markBackendStateRetired` and sets the request signal created by `provider.WithBackendStateRetirement`; `provider.BackendStateRetired` and `provider.BackendStateRetirementSignaled` report the retirement. An acquire failure, and a failed cold reseed with no live parent, retire nothing, so their errors stay unmarked; a successful cold reseed still carries `ClearBackendState` on its terminal chunk. A fork helper runs under `key + claudeSubSummarySuffix` and leaves the parent process and its state untouched, so it clears nothing.

## Usage gate

Before a new user message is written, `get_usage` is polled. The refusal rules are in the [extra usage safety gate](../user/claude-subscription.md#extra-usage-safety-gate). Unconfirmed states, including missing fields, are retried with 500ms, 1s, then 2s backoff for up to 15 seconds (`claudeSubUsageGateBudget`). Each `get_usage` is bounded by the 30 second control timeout.

If the live process still cannot confirm, `confirmUsageFresh` asks a new CLI process once, because the CLI caches an incomplete usage read in the running process. Confirmation is serialized pool-wide and bounded to 8 seconds (`claudeSubUsageProbeTimeout`). For advisor calls, only a second fresh usage result that is still definitively not-ready permits the pool-owned `confirmAuthFresh` job to inspect auth status. Credits enabled, cancellation, shutdown, and any successful or unknown usage result retain precedence, so auth cannot authorize a turn or weaken the fail-closed gate. Cancellation, a deadline, or shutdown that arrives during fresh auth overrides the earlier usage refusal.

A `rate_limit_event` whose `rate_limit_info.status` is `rejected` for a plain, non-overage limit becomes a `*UsageLimitError` (`claudeSubRateLimitVerdict`). It ends the turn. Within this provider, `claudeSubRetryDecision` never recovers it, and `claudeSubSummaryTurn` returns it instead of replaying a failed summary fork on the live parent. The shared provider and agent retry paths stop on `AsUsageLimit` (`classifyProviderError`, `RetryableProviderError`, and the agent runner's usage-limit stop reason).

## Provider diagnostics

When a stream-error logger is configured, each model call writes one provider-stream record (`claudeSubStream`) with transport `cli` and `attempts` 1. `call_kind` is `advisor`, `summary`, `sub_agent`, or `normal` (`claudeSubCallKind`), in that precedence. The record carries outcome, duration, chunk count, time to first token, and a bounded error. CLI result text, the stderr tail, and control-response text are not recorded. `partial_stream` is set when chunks reached the caller before the failure. Records have no request URL, headers, or bodies, because the CLI has no HTTP exchange. A CLI decode failure (`errClaudeSubDecodeStream`) is classified `decode_error`.

The cache diagnostics record carries the call's claude_subscription measurements (`claudeSubCallMetrics`): `claudesub_process`, `claudesub_reseed_reason`, `claudesub_recovery`, the usage gate's time and poll count, the probe flag, and the sync mismatch fields. A live process that refuses the request is compared with `claudeSubSync.planMismatch` (`claudesub_sync.go`), which reports the first failed request position, that position's role, and one fixed check label: `role`, `digest`, `images`, `tool_calls`, `shape`, or `length`. The entry comparison decides both the refusal and the reported position, so a request that is shorter than the record and also rewrites its prefix reports the rewrite. `claudeSubLiveAccepts` records the mismatch with `claudeSubCallMetrics.noteSyncMismatch`. Only bounded values are kept: no message content, digest, tool-call id, path, identifier or image data, and the position is clamped to `claudeSubSyncMismatchMaxIndex`. A mismatch is reported only while the call still reseeds because of it: `claudeSubCallMetrics.clearReseed` drops it when the request is resumed instead, `claudeSubCallMetrics.noteReseed` drops it for every other reseed branch, and `claudeSubCallMetrics.resetDelivery` drops it when the call replaces the attempt before retrying it or after a parent summary falls back from its fork. Restore checks and the summary plans report no request position, so they leave the fields absent and the reseed reason alone.

## Live interrupt probe

`TestClaudeSubProbe` (`claudesub_probe_test.go`) is an opt-in harness that measures the CLI's interrupt and resume behaviour against a real signed-in CLI. It records, per experiment, the ordering of an `interrupt` control response and the turn's terminal result, the result's subtype, `terminal_reason`, `is_error` and `stop_reason`, events that arrive after the result, what happens to a `tools/call` that is in flight when the interrupt lands, whether an interrupt that races a finished turn yields a stray result, whether `--resume-session-at` truncates the on-disk transcript or only hides later entries, and each turn's cache counters. E7 additionally measures the join a crashed turn needs: it SIGKILLs a persisted CLI child it spawned while that child streams a list, then resumes a fork at the earlier assistant uuid and sends one user line carrying the original prompt plus the quoted partial and a continuation note.

The `claudesub_probe` build tag keeps the file out of the package, so `go test ./...`, vet and lint without the tag never compile it. `STEINER_CLAUDESUB_PROBE` selects the mode, and an unset value skips the test.

```bash
STEINER_CLAUDESUB_PROBE=plan go test -tags claudesub_probe -count=1 -timeout 30m -run TestClaudeSubProbe -v ./internal/provider
STEINER_CLAUDESUB_PROBE=run STEINER_CLAUDESUB_PROBE_ACK=i-accept-live-requests \
  go test -tags claudesub_probe -count=1 -timeout 30m -run TestClaudeSubProbe -v ./internal/provider
STEINER_CLAUDESUB_PROBE=run STEINER_CLAUDESUB_PROBE_ACK=i-accept-live-requests STEINER_CLAUDESUB_PROBE_ONLY=E7 go test -tags claudesub_probe -count=1 -timeout 30m -run TestClaudeSubProbe -v ./internal/provider
```

The `-timeout 30m` suits the probe's own 25 minute ceiling: the probe stops with its own message first, and a shorter `-timeout` would cut the run before its report is written.

`plan` resolves the CLI on `PATH` without executing it and prints the argv `claudeSubArgs` builds for each experiment with the load-deciding switches (`--setting-sources`, `--strict-mcp-config`, `--tools`, `--allowedTools`) marked present or absent, the child environment keys from `claudeSubSessionEnv` with values redacted except `CLAUDE_CODE_RESUME_INTERRUPTED_TURN`, `CLAUDE_CODE_RESUME_SHOWS_CUT_OFF_CALLS`, `CLAUDE_CODE_RESUME_PROMPT`, `CLAUDE_CONFIG_DIR` and `HOME`, the working directory, report and raw-capture paths it would create, the expected CLI session-store directory, the model, the experiment selection with the selected experiments' bounds, and the experiment list. It starts no process and creates nothing. `run` additionally requires the acknowledgement variable above, because it spends real subscription requests and writes CLI session files under the CLI configuration directory.

`STEINER_CLAUDESUB_PROBE_MODEL` sets the model (default `haiku`), `STEINER_CLAUDESUB_PROBE_OUT` sets the report path (default `report.json` in a private temporary root with mode `0700` and mode `0600` on the file), and `STEINER_CLAUDESUB_PROBE_CLEANUP=1` removes the transcript files of the session ids the probe itself recorded. Cleanup accepts only ids matching `[A-Za-z0-9-]+` and only removes a file whose directory is exactly the probe's own project directory; every other recorded id is skipped and reported. `STEINER_CLAUDESUB_PROBE_ONLY` is a comma-separated list of experiment ID prefixes (`E7`, `E1,E7`) and runs only the matching experiments, in table order; an unknown prefix or an empty entry fails before anything is spawned. `STEINER_CLAUDESUB_PROBE_E7_TRIALS` sets E7's trial count (1 to 5) and fails when the selected experiments cannot fit that count inside the ceiling.

Processes start through the production pool (`acquire` and `startClaudeSubSession`), so argv, child environment and the loopback MCP host match a normal session. Before init, the spawn seam asserts the argv carries `--strict-mcp-config`, an empty `--setting-sources`, a single `--tools` with an empty value and a single `--allowedTools` for the steiner prefix. Each experiment uses a fresh process and an empty private working directory, publishes one synthetic MCP tool (`probe_wait`), and sends only prompts carrying `PROBE-` markers. A wrapper on the pool's spawn seam records every line in both directions, including control responses the router consumes before they reach the event queue.

The first prompt is gated on the init event. The production session path sends no `initialize` request, and the CLI may report `system`/`init` only after the first user input, so the probe waits 10 seconds for init before writing anything. If init arrives, it is validated directly (`init before input`). If it does not, the probe sends one gating turn and holds every other prompt until init validates. For the non-persisted specs the gating turn is a fixed warmup prompt (`PROBE-WARMUP: reply with the single word ok and do not call any tool`), so no experiment turn is spent on it; for the persisted and resumed processes it is the experiment's own first tool-free prompt (T1 for the parent, T4 for E5's resume and fork processes, the two-block continuation line for E7's resumed fork), so no extra turn enters a stored transcript. While the gating turn runs, and until its own result arrives, any MCP tool call is resolved with an error result and the rejected call ids are reported. Init must arrive and validate within 20 seconds of the gating turn, otherwise the experiment fails. Validation requires the tool list to be exactly `mcp__steiner__probe_wait`, the model to be the requested one or its resolved id, and no MCP server other than `steiner`; `sendPrompt` refuses to write until a process's init has passed. The report states which path happened and records the init event's tools, model, capabilities, CLI version, permission mode and the names in its `plugins`, `mcp_servers`, `slash_commands`, `agents`, `skills` and any hook field, because those are the evidence of what a user configuration loads into a steiner process. A warmup turn is recorded as its own turn, so cache comparisons start at the turn after it.

Each experiment is bounded by its own worst case: 180, 190, 170, 150, 340, 190 and 189 seconds, each above the sum of that experiment's step budgets (including the init gate, the 30 second interrupt control timeout, the tails and a teardown term per started process of two `claudeSubCloseGrace` waits plus a margin). The experiment body spends the same declared step list the bound is checked against, so the two cannot drift, and a self-check pins both relations. The probe's own ceiling is 25 minutes, below the required `-timeout 30m`, so it stops with its own message first. Every experiment fails soft with its error recorded. Each process is always torn down through `retireAndRelease`, and the report records the exit status (or that it is unknown because a bounded teardown left the child unreaped), the child's wait error, the teardown result, the connection error and the number of recorded events the probe never read. An experiment fails when its timeline hit the entry cap, when the process exited before teardown began, or when teardown reported an error other than a bounded teardown that ran out of deadline; a non-zero exit after the probe's own stdin close is recorded evidence, not a failure.

E7 runs one trial in a full run: each trial starts two persisted processes, so it spends both processes' init gates, four waits and two per-process teardown budgets, and E1 to E6 with their teardowns already claim most of the 25 minute ceiling. When E7 is the only selected experiment it derives three trials from the freed budget, and `STEINER_CLAUDESUB_PROBE_E7_TRIALS` overrides the count; the experiment's bound is its own per-trial plan times the resolved count, and a selection that cannot fit the requested count inside the ceiling fails before anything is spawned, as does selecting E7 on a platform without the kill seam. It kills only the CLI child it spawned: `claudeSubProbeKillProcess` reaches the process handle through the connection the spawn seam returned and sends SIGKILL to that process alone, so no other process is ever signalled, and the coordinator's own tree termination still runs at teardown. A trial fails when the killed turn already carried its result at the kill point (`finished before kill`), when the exit is anything but status `-1` with a `signal: killed` wait error (`exited before kill`), or when the resumed turn ends with an error result. The killed process is marked `ExpectedCrash`, which exempts only that SIGKILL exit and a teardown result carrying `signal: killed` or the bounded-teardown allowlist; any other teardown error still fails. The quoted partial is read only after the process exited and its events were drained, and the resumed process's init gate gets the experiment's declared continuation budget for that turn's result. The continuation note tells the model that the quoted text ends exactly at the end marker, so a reply whose next character should be a line break or a space starts with it. Each trial reports the tail of the partial, the head of the continuation, the item numbers either side of the seam with duplicates, gaps, whether the continuation finished a cut item number and whether a whole final item number was joined with no line break, whether the model mentioned the interruption, the continuation's four cache counters, the fork's session id, and a verdict in this precedence: `empty` (no text or an error result), `no-items`, `restart`, `duplicate`, `gap`, `line-break-missing` (the partial's final item number is whole and the continuation starts the next item with no line break between them), `short` (the list stops before item 200), `commentary`, and `clean`, with aggregate counts across the trials. Cleanup records both the original and the forked session ids.

The report is JSON: CLI version, redacted environment shape, argv and load-deciding switches per process, per-experiment timelines, MCP call samples with each call's outcome (waiting, result stored, claimed by a late result, cancelled or closed by host teardown), transcript snapshots (line counts and entry types and uuids, never content) and derived findings. The report and the raw stdout capture always live inside the probe's private temporary root, which is kept after the run; an inherited `STEINER_CLAUDESUB_RECORD` is overridden, so capture never lands elsewhere. Results are evidence for the CLI version and account they ran on, not a protocol guarantee.

## Model discovery

Discovery runs a short-lived CLI under a 20 second outer budget (`claudeSubDiscoveryTimeout`): 12 seconds for work and 8 seconds reserved for cleanup. It reads the `initialize` response, skips the `default` alias, and keeps the first entry for each resolved model ID. Failure or an empty usable result returns the static fallback catalog.
