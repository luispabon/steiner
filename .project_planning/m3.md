# MiniMax M3 / OpenCode Go Automatic Transport Plan

## Goal

Make Steiner handle OpenCode Go models the way OpenCode does: one configured
`opencode-go` provider should work for both OpenAI-compatible models
(`kimi-k2.6`, `deepseek-v4-pro`, `glm-5.1`, etc.) and Anthropic Messages models
(`minimax-m3`, `minimax-m2.7`, `minimax-m2.5`, `qwen3.7-*`) without requiring the
user to split provider aliases manually.

The core fix is per-model effective transport resolution from `models.dev/api.json`,
plus a real Anthropic Messages provider implementation. MiniMax-specific
OpenAI-chat parsing is only a fallback; the primary OpenCode Go MiniMax path is
Anthropic `/messages`.

## Evidence And Key Decisions

- OpenCode Go publishes a mixed transport surface:
  - OpenAI-compatible `/chat/completions` for Kimi, DeepSeek, GLM, MiMo.
  - Anthropic `/messages` for MiniMax M3/M2.x and Qwen3.7.
- Live `models.dev/api.json` for `opencode-go` exposes this as:
  - Provider root `npm: "@ai-sdk/openai-compatible"`.
  - Model-level `provider.npm: "@ai-sdk/anthropic"` for `minimax-m3`,
    `minimax-m2.7`, `minimax-m2.5`, `qwen3.7-max`, and related models.
  - `interleaved.field: "reasoning_content"` for several OpenAI-compatible
    reasoning models such as Kimi, DeepSeek, and GLM.
- Steiner currently validates `anthropic` as a provider type, but the runtime
factory always constructs `OpenAICompat`, so the type is not actually honored.
- Do not hardcode `minimax-m3` as the transport trigger. Use metadata first,
explicit config second, and configured provider type as fallback.

## Stage 1: Model Metadata Transport Resolution

### Intent

Teach Steiner to resolve an effective provider transport per model from
`models.dev/api.json`, while preserving existing limit and reasoning metadata
behavior.

### Main Files

- `internal/metadata/lookup.go`
- `internal/metadata/lookup_test.go`
- `internal/provider/resolved_model.go`
- `internal/provider/resolved_model_test.go`
- `internal/provider/types.go` or `internal/provider/resolved_model.go`
- `internal/config/config.go`
- `internal/config/patch.go`
- `internal/config/patch_model.go`
- `internal/config/validate_model.go`
- `docs/CONFIGURATION.md`

### Implementation Details

- Extend `metadata.ModelInfo` with transport-related fields:
  - `ProviderNPM string`
  - `ProviderAPI string`
  - `ModelProviderNPM string`
  - `ModelProviderAPI string`
  - `InterleavedField string`
- Update `LookupWithProvider` so it can read both provider root fields and the
  matched model entry:
  - Provider root `npm`.
  - Provider root `api`.
  - Model-level `provider.npm`.
  - Model-level `provider.api` if present.
  - Existing `limit.context`, `limit.output`, and `interleaved.field`.
- Add a normalized transport type to the resolved model layer, for example:
  - `ProviderTransportOpenAICompat`
  - `ProviderTransportAnthropic`
  - `ProviderTransportConfigured`
- Add `ResolvedModel.EffectiveProviderType config.ProviderType` or equivalent.
  - If no metadata override exists, this equals `rm.ProviderConfig.Type`.
  - If metadata says `@ai-sdk/anthropic`, effective type is `anthropic`.
  - If metadata says `@ai-sdk/openai-compatible`, effective type is
    `openai_compat`.
- Add optional config override:
  - `models.<alias>.advanced.transport: auto | openai_compat | anthropic`
  - Default is `auto`.
  - Explicit `openai_compat` or `anthropic` wins over models.dev.
  - `auto` means use metadata if exact transport is available, else provider
    config type.
- Do not override a user-configured `base_url` by default.
  - For this first implementation, use metadata transport but keep configured
    provider `BaseURL`, because existing Steiner config already supplies
    `https://opencode.ai/zen/go/v1`.
  - Record metadata API URL in `ResolvedModel` diagnostics/warnings if useful,
    but do not silently switch base URLs unless a later config policy supports
    it.
- Preserve current `ReasoningEchoBack` behavior:
  - `interleaved.field == "reasoning_content"` still enables echo-back when
    config does not override it.
  - Unknown interleaved fields do not trigger unsupported behavior.

### Acceptance Criteria

- `opencode-go` + `minimax-m3` resolves to effective provider type `anthropic`
  when models.dev metadata is available.
- `opencode-go` + `kimi-k2.6` resolves to effective provider type
  `openai_compat`.
- Explicit `advanced.transport: openai_compat` forces MiniMax M3 back onto
  OpenAI-compatible transport.
- Existing configs with no metadata cache or network access behave as before.

### Tests

- Add table tests with synthetic models.dev JSON for:
  - Provider root OpenAI-compatible plus model-level Anthropic override.
  - Provider root OpenAI-compatible with no model override.
  - Provider root Anthropic.
  - Explicit config override winning over metadata.
  - Unknown `npm` values falling back to configured provider type.

## Stage 2: Runtime Provider Factory Dispatch

### Intent

Make runtime construction honor the resolved effective provider type instead of
always creating `OpenAICompat`.

### Main Files

- `cmd/steiner/runtime_build.go`
- `cmd/steiner/runtime_build_test.go`
- `cmd/steiner/main.go`
- `internal/provider/interface.go`

### Implementation Details

- Add a provider constructor variable for Anthropic, matching the existing
  testable `newOpenAICompat` pattern.
- Update `buildRuntimeProviderFactory`:
  - Switch on `rm.EffectiveProviderType` if set.
  - Fall back to `rm.ProviderConfig.Type` for older/zero-value resolved models.
  - `openai_compat`, `ollama`, `lmstudio`, `openrouter`, `openai`, and `litellm`
    continue to use `OpenAICompat` for now.
  - `anthropic` uses the new Anthropic provider.
  - Unsupported native provider types should return a clear error rather than
    silently using OpenAI-compatible transport.
- Ensure scheduler, retry config, timeout, headers, API key, and HTTP client are
  passed consistently to both provider constructors.

### Acceptance Criteria

- Runtime creates Anthropic provider for `ResolvedModel.EffectiveProviderType ==
  anthropic`.
- Existing OpenAI-compatible configs still construct `OpenAICompat`.
- A provider type validated in config but not implemented fails with a clear
  message unless it is intentionally mapped to OpenAI-compatible.

### Tests

- Unit-test provider factory dispatch with stub constructor variables.
- Regression-test existing OpenAI-compatible factory behavior.
- Add a test proving `anthropic` is no longer routed to `OpenAICompat`.

## Stage 3: Anthropic Messages Provider

### Intent

Implement Steiner's normalized `Provider` interface for Anthropic Messages,
including streaming, tool calls, thinking blocks, and tool-result replay.

### Main Files

- `internal/provider/anthropic.go`
- `internal/provider/anthropic_wire.go`
- `internal/provider/anthropic_stream.go`
- `internal/provider/anthropic_test.go`
- `internal/provider/anthropic_stream_test.go`
- `internal/provider/types.go`

### Request Mapping

- Endpoint:
  - Base URL from config plus `/messages`.
  - For `https://opencode.ai/zen/go/v1`, final endpoint is
    `https://opencode.ai/zen/go/v1/messages`.
- Headers:
  - `Content-Type: application/json`
  - `Accept: text/event-stream` for streaming
  - `Authorization: Bearer <api_key>` when configured
  - `anthropic-version: 2023-06-01` unless user already provided one
  - Preserve user headers.
- Request body:
  - `model`
  - `max_tokens` from `ChatRequest.MaxTokens` or model effective output limit
    path if already set upstream
  - `system` from system messages
  - `messages` for user/assistant/tool turns
  - `tools`
  - `stream`
  - merged `Params` and `ExtraParams` using the same precedence style as
    OpenAI-compatible requests.
- Message conversion:
  - System messages become Anthropic `system` text blocks.
  - User messages become `role: user`, `content: [{type:"text", text: ...}]`.
  - Assistant messages include ordered content blocks:
    - Existing `ReasoningContent` as `thinking` if replay is supported.
    - Text content as `text`.
    - `ToolCalls` as `tool_use` blocks with `id`, `name`, and `input`.
  - Tool result messages become Anthropic user messages containing
    `tool_result` blocks with `tool_use_id` and text content.

### Response Mapping

- Non-stream response:
  - `content[].type == "thinking"` -> `Message.ReasoningContent`
  - `content[].type == "text"` -> `Message.Content`
  - `content[].type == "tool_use"` -> `Message.ToolCalls`
  - `stop_reason == "tool_use"` maps to a tool-call finish reason.
  - Usage maps into `UsageStats`.
- Streaming response:
  - Handle Anthropic SSE event types:
    - `message_start`
    - `content_block_start`
    - `content_block_delta`
    - `content_block_stop`
    - `message_delta`
    - `message_stop`
    - `error`
  - Emit `ChatChunk{Thinking: ...}` for thinking deltas.
  - Emit assistant content deltas for text.
  - Accumulate `tool_use` JSON input fragments by content block index.
  - Final chunk includes full normalized message, usage, finish reason, and
    `Done: true`.
- Preserve enough provider-native metadata for future replay:
  - If thinking signatures appear, add a small internal field for provider
    metadata rather than dropping them. If the existing `provider.Message` shape
    cannot carry it cleanly, add a typed metadata map and round-trip it through
    `agent.Message`.
  - If signatures are absent on OpenCode Go MiniMax, this metadata path can
    still be tested with synthetic Anthropic fixtures.

### Acceptance Criteria

- Anthropic tool-use responses drive the existing agent `executeToolCalls` flow.
- Anthropic thinking appears as TUI/log thinking chunks and does not pollute
  normal assistant text.
- Tool results are replayed in Anthropic-compatible format.
- Streaming and non-streaming paths produce equivalent final `ChatResponse`
  values.

### Tests

- Request marshaling tests for:
  - Basic user prompt.
  - Assistant tool call plus tool result replay.
  - Thinking + text + tool_use replay.
  - Extra params merging.
- Non-stream response tests for:
  - Text-only answer.
  - Thinking + tool_use.
  - Multiple content blocks.
- Stream tests for:
  - Thinking deltas.
  - Text deltas.
  - Tool input JSON deltas split across events.
  - Error events.
  - Missing final event handling.

## Stage 4: OpenAI-Compatible Fallback Hardening

### Intent

Keep OpenAI-compatible MiniMax and other reasoning models from degrading, even
though this is not the primary OpenCode Go MiniMax path.

### Main Files

- `internal/provider/openai_wire.go`
- `internal/provider/openai_stream.go`
- `internal/provider/openai_wire_test.go`
- `internal/provider/openai_stream_test.go`

### Implementation Details

- Add `reasoning_details` to OpenAI-compatible wire structs.
  - Accept arrays containing text-like entries.
  - Normalize them into `Message.ReasoningContent`.
  - Replay them if provider metadata indicates this is required, or if they
    were present in the prior assistant message.
- Keep existing `reasoning_content` behavior unchanged.
- Improve stream EOF handling:
  - EOF before `[DONE]` remains retryable when there has been no final usable
    chunk.
  - EOF after a complete final chunk or provider-equivalent finish state should
    not create duplicate retry output.
- Do not add broad `<think>` parsing unless needed by tests or real provider
  evidence. OpenCode does not rely on a runtime inline-think parser for its M3
  path.

### Acceptance Criteria

- Existing OpenAI-compatible tests pass unchanged.
- `reasoning_details` responses do not lose thinking content.
- Tool calls still execute when content is empty or only whitespace.

### Tests

- Non-stream response with `reasoning_details` + `tool_calls`.
- Streamed `delta.reasoning_details`.
- EOF after final usable event.
- Regression tests for `reasoning_content`.

## Stage 5: Agent Message Metadata Round Trip

### Intent

Ensure provider-native reasoning metadata survives conversation replay when a
transport requires it, without leaking transport details into prompt assembly
more than necessary.

### Main Files

- `internal/provider/types.go`
- `internal/agent/types.go`
- `internal/agent/message_convert.go`
- `internal/agent/message_convert_test.go`
- `internal/prompt/assemble.go`
- `internal/prompt/masking.go`

### Implementation Details

- If Stage 3 discovers Anthropic signatures or native metadata must be replayed,
  add a minimal metadata field:
  - Prefer `ProviderMetadata map[string]any` or typed sub-structs over ad hoc
    string fields.
  - Preserve metadata only on assistant reasoning/tool-call messages where it is
    required.
- Update conversions:
  - `provider.Message` -> `agent.Message`
  - `agent.Message` -> `provider.Message`
  - Replay-safe conversation transforms
  - Masking/compaction rules so metadata for active tool-call turns is not lost.
- Avoid exposing metadata in user-visible final output.

### Acceptance Criteria

- Anthropic thinking/tool metadata round-trips through an assistant tool-call
  turn and the following tool-result turn.
- Existing prompt assembly order and context masking behavior remains stable.

### Tests

- Message conversion metadata round-trip.
- Prompt masking preserves metadata for recent tool-call exchanges.
- Compaction does not corrupt active tool-call/tool-result pairs.

## Stage 6: Config, Docs, And User-Facing Diagnostics

### Intent

Make automatic transport behavior discoverable and debuggable.

### Main Files

- `docs/CONFIGURATION.md`
- `README.md`
- `internal/output/provider_diagnostic.go`
- `internal/output/event_constructors.go`
- `cmd/steiner/cmd_model.go`
- Relevant tests for config/model output.

### Implementation Details

- Document `advanced.transport`.
- Document automatic models.dev transport resolution:
  - Metadata can override the configured provider type per model.
  - Explicit `advanced.transport` wins.
  - If metadata is unavailable, configured provider type wins.
- Add or update model inspection output to show:
  - Configured provider type.
  - Effective provider type.
  - Metadata source.
  - Any transport override reason.
- Add a diagnostic when effective transport differs from configured provider
  type, for example:
  - `model minimax-m3 uses anthropic transport from models.dev provider override`
- Update README only if a high-level configuration example is already present
  or if the config docs are insufficient for users to discover the behavior.

### Acceptance Criteria

- Users can see why `opencode-go/minimax-m3` is using Anthropic transport.
- Users can override bad metadata without redefining provider aliases.
- Documentation includes the one-provider OpenCode Go example.

### Tests

- Config docs are not directly testable, but command/model output tests should
  cover effective transport display if such output exists.

## Stage 7: Integration Verification

### Intent

Prove the change does not break existing OpenAI-compatible models while fixing
MiniMax M3 transport.

### Targeted Checks

Run these before broad checks:

```bash
go test ./internal/metadata
go test ./internal/provider
go test ./internal/agent
go test ./cmd/steiner
```

If Anthropic provider tests are expensive or flaky, keep them unit-level with
`httptest.Server` fixtures rather than live provider calls.

### Broad Checks

Before finalizing Go changes, follow repository instructions:

```bash
make check
```

If `make check` cannot run, report the exact command and failure reason.

## Rollout Order

1. Implement metadata transport resolution first, with no runtime behavior
   change except resolved-model fields and tests.
2. Add runtime factory dispatch with Anthropic provider stub returning an
   intentional not-implemented error, then replace the stub in Stage 3.
3. Implement Anthropic non-streaming path.
4. Implement Anthropic streaming path.
5. Add OpenAI-compatible fallback hardening.
6. Add docs/diagnostics.
7. Run targeted tests and `make check`.

## Risks

- Anthropic thinking signatures may be required for some providers and absent
  in Steiner's current message model. Mitigation: add provider metadata
  round-trip only where required.
- `models.dev/api.json` can change. Mitigation: fallback to configured provider
  type and allow explicit `advanced.transport`.
- OpenCode docs and live registry may disagree. Mitigation: use live/cached
  registry for automatic behavior and expose diagnostics showing the decision.
- Transport switching changes endpoint path. Mitigation: effective type decides
  only request protocol/path; provider alias, auth, headers, and base URL remain
  stable.

## Non-Goals

- Do not implement every native provider type (`gemini`, native `openai`, etc.)
  in this change.
- Do not build a full OpenCode catalog importer.
- Do not hardcode a MiniMax model allowlist for transport selection.
- Do not rely on inline `<think>` parsing as the primary MiniMax M3 fix.
